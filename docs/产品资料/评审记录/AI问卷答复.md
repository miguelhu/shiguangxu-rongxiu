## 1. 问卷逐项答复

| 问题 | 本版答复 | 依据与落地 |
| --- | --- | --- |
| Q1 全部做模型生成吗 | 采用混合方式；表达加工调用模型，邀请骨架固定，空白祝福用静态起笔 | AI-01—07、09按任务调用；AI-08不调用模型。排序、拼图、通知、计数、二维码为规则；不能全塞一个写作Prompt |
| Q2 动作还是文风 | 两层：先明确任务／动作，再提供适用风格 | 沿用四风格自然口述、文辞柔美、沉静大气、郑重真诚；普通文案默认自然口述。ASR、标签、检索、执行无风格选择；总信首次生成不强制选风格。详见10第3章 |
| Q3 照片说明看图吗 | AI-02只处理用户文字或确认转写 | 不把图片、文件名、EXIF、上传顺序当叙事事实；AI-14分类、AI-22修复是独立能力，不偷塞进02 |
| Q4 总信输入谁批准、带什么 | 用户确认本人稿和用途；有效统筹审核并批准进入总信；最后统筹确认总信 | 提交不等于批准。服务端先筛选批准且未撤回的源，保存sourceRef、作者、授权、revision及hash。模型收到必要的匿名来源标记和叙述归属，不接收不必要账号资料 |
| Q5 总信生成到哪一层 | 首版生成正文；标题、称呼、结尾固定祝语、署名由模板或统筹编辑 | 可按主题重排，但不制造时间因果。默认无小标题；明确模板需要才增加固定分段。集体声音只表达获准共同祝愿，个人经历带来源归属；未获全体授权不能署“全体同事”。最终确认人为有效统筹，模型不能自批准 |
| Q6 邀请模型负责什么 | 仅已有寄语润色 | 主办方、日期、收集截止、二维码、跳转链接由业务拼装；空输入先显示固定模板，不靠模型编活动信息 |
| Q7 邀请包括哪些 | 当前落地共创邀请；交付／领取邀请独立场景预留 | 现有CO.G01有共创依据。不能把算法提议“两类都做”当成已确认新页面；若启用交付邀请，仍复用AI-07，但scene、模板、授权、渠道和触发事件单独配置 |
| Q8 祝福空输入如何处理 | 静态起笔，选择后进入用户草稿 | AI-08提供2—3个短模板；AI-04仅对有内容稿加工。不得制造用户经历或自动提交 |
| Q9 局部修改怎么做 | AI-09独立动作，选区候选、差异对比、采用与撤销 | 输入当前letterId、revision和选区；不动选区外正文、署名、来源及AI标识；采用后产生新版本并使旧确认失效；全信重新生成走AI-05 |
| Q10 可见性、Memory及留存 | 按项目角色和用途；荣休不自动写长期画像；历史素材复用需显式选择且权限仍有效 | 投稿者不默认看他人；统筹可人工看获准提交待审稿，但不能将待审稿喂总信；受礼者按拆封用途读成品。长者个人记忆与荣休项目隔离；留存建议见10第8章，生产期限仍需定案 |

### Q4 的重要修正

“模型只负责正文”正确，但不能演变为“模型完全不知道谁说了什么”。如果把多人的话无标记拼接，后端事后附sourceRef也修复不了已经写错的人称。建议模型输入保留`source_A／source_B`、作者与亲历者的语义关系、获准显示名或匿名代称；真实账号、审批过程和长期映射留服务端。输出段落附临时引用，由服务端映射校验；展示给受礼者的来源不包含内部审核意见。

### Q5 的零素材与少素材

无可用素材不生成“有故事的总信”；提示先审核素材。只有祝愿时可形成简短信件，不凑人物生平。正式交付是否允许纯模板或人工信作为降级，关联01的最小成品D-03，由产品冻结；不能由算法为了避免空结果自行发布。

## 5. 产品和算法交接时直接带走的结论

1. 荣休优先实现AI-01—09及必要ASR、质量检测；AI-08是模板。集体信需全链路审核，不仅交付一个Prompt。
2. 同一能力跨端同号，按11识别每页是生成、消费还是执行；权限和内容版本不能因共用模型而共享。
3. 四文风和同源例句见10第3.3节，动作适用矩阵见3.2节。前端可以先完成标准控件、候选对比和异常态。
4. 问卷十项已有可执行答复；上表保留真正需要业务／服务方定案的生产门禁。算法无需再靠猜测补产品。
